# ADR-009 包结构分层与限界上下文物理分离

- **维护人**：PO（唐志烽 / luck970）

## 一、背景

Lab 3 的事件风暴把 CampusOverflow 划为四个业务限界上下文：身份与课程（谁能提问）、问答（问题如何流动）、声誉（贡献如何被激励）、检索与通知（信息如何找到人）。Lab 4 要求把这些边界**物理落到 Maven 模块与 Java 包**上，而不是停留在文档里，同时满足三个约束：

1. 按 DDD 分层组织代码，`domain` 层不得被框架细节污染；
2. 核心聚合（User / Question / Answer）的 Setter 私有化，不变式由聚合自身保护；
3. `QuestionRepository` 接口定义在 `domain` 层、实现在 `infrastructure` 层（依赖倒置）。

若不把边界编码进构建结构，模块化单体就会退化为「一个包里什么都能 import」的单体，ADR-001 的约束将只能靠人工评审维持。

## 二、决策

### 2.1 模块树

`campus-overflow-student/backend/` 由 1 个父 POM + 1 个启动装配模块 + 1 个共享内核 + 4 个上下文聚合模块构成，共 **27 个 POM**：

```
backend/
├── pom.xml                          父 POM：统一 Spring Boot 3.x / JDK 21 / JUnit 5 版本
├── co-bootstrap/                    启动入口与上下文装配（CampusOverflowApplication）
├── co-shared-kernel/                共享内核：跨上下文复用的值对象与通用类型
├── co-identity/                     身份与课程上下文
│   ├── co-identity-api/             对外契约（DTO / 集成事件声明）
│   ├── co-identity-domain/          聚合、实体、值对象、仓储接口（无框架依赖）
│   ├── co-identity-application/     应用服务、事务边界、命令编排
│   ├── co-identity-infrastructure/ JPA 实体与仓储实现、外部适配器
│   └── co-identity-interfaces/      REST Controller、请求/响应模型
├── co-qa/                           问答上下文（同 5 层）
├── co-reputation/                   声誉上下文（同 5 层）
└── co-discovery/                    检索与通知上下文（同 5 层）
```

课程 PDF 要求「每个子域模块内部分 domain / application / infrastructure / interface 四层」。本仓库在此基础上增加 `*-api` 一层，用于承载 ADR-007「契约优先」下的跨上下文契约与集成事件声明，避免上下文之间直接依赖对方的 `domain`。四层职责保持不变。

### 2.2 六条结构规则

| 编号 | 规则 | 强制方式 |
| --- | --- | --- |
| FF-1 | `domain` 不得依赖 Spring / JPA / 任何 `infrastructure` 包 | ArchUnit `ArchitectureTest` |
| FF-2 | `interfaces → application → domain`，反向依赖禁止 | 同上 + Maven 模块依赖 |
| FF-3 | `infrastructure` 实现 `domain` 定义的仓储接口，不得反向被 `domain` 依赖 | 同上 |
| FF-4 | 跨上下文只允许依赖 `*-api` 或通过集成事件（ADR-002 事务性发件箱）通信 | 同上 |
| FF-5 | 领域对象与 JPA 实体分离，聚合内不出现 `@Entity` / `@Table`（ADR-008） | 同上 |
| FF-6 | `co-bootstrap` 是唯一装配点，各上下文不得自行启动 Spring 容器 | 同上 |

规则由 `co-bootstrap` 中的 `ArchitectureTest` 在 `mvn test` 阶段执行；CI 的「架构约束检查」步骤以 `-pl co-bootstrap -am` 单独运行该测试，违反分层在构建期即失败，不依赖人工评审。

### 2.3 分层内的职责边界

- **domain**：聚合根、实体、值对象、领域事件、仓储**接口**、不变式校验。所有 Setter 私有，状态变更只经工厂方法或聚合方法（如 `Question.post()`、`Question.acceptAnswer()`）。
- **application**：用例编排、事务边界、调用仓储接口，不包含业务规则。
- **infrastructure**：JPA Entity 与领域对象的双向映射、`QuestionRepositoryImpl`、Flyway 迁移脚本（按上下文分目录）、Logback JSON 日志、`@RestControllerAdvice` 全局异常处理。
- **interfaces**：`QuestionController.create()` 接收 `POST /api/v1/questions`，把请求模型转成应用服务入参。
- **api**：跨上下文的契约 DTO 与集成事件声明，是唯一允许被其他上下文引用的包。

### 2.4 目录决策

- ADR 文档跟随工程目录存放于 `campus-overflow-student/docs/adr/`，不搬迁，以保留既有链接与 `git log --follow` 历史；
- 实验提交物文档按 Lab 分目录存放于仓库根 `docs/lab4/`、`docs/lab5/`，便于教师按实验检索；
- 领域建模产物位于 `docs/ddd/`。

## 三、后果

**正面**

- 业务边界在编译期与构建期双重可见：跨上下文违规 import 会直接导致 `mvn test` 失败；
- `domain` 无框架依赖，聚合行为可用纯 JUnit 覆盖（当前基线 18 个测试类 / 91 个用例，0 失败）；
- 每个上下文可独立替换持久化实现或接口层，为后续演进留出接缝。

**负面 / 代价**

- 27 个模块使首次 `mvn clean install` 的耗时与 POM 维护成本上升；
- 跨上下文协作必须经 `*-api` 或发件箱事件，简单查询也要多写一层契约，短期开发速度下降；
- 模块化单体的强一致性依赖「约束靠测试而非进程隔离」，一旦有人绕过 `ArchitectureTest`（例如把规则排除），边界会在无人察觉时腐化。

**风险与缓解**

- 风险：`*-api` 逐渐膨胀成新的「公共大包」。缓解：只允许放契约与事件声明，禁止放实现类；由 FF-4 与 PR 评审共同把关。
- 风险：JPA 与领域对象映射代码重复。缓解：映射集中在 `infrastructure` 层，ADR-008 已记录该取舍。

## 四、被否决的替代方案

| 方案 | 否决理由 |
| --- | --- |
| 按技术层分包（全局 `controller/` `service/` `repository/`） | 以技术视角组织，限界上下文边界不可见；跨上下文随意引用无法在构建期拦截，直接违背 Lab 4 评分要点「按 DDD 限界上下文物理分包」。 |
| 单模块 + 包命名隔离（仅靠 `com.xxx.qa.*` 前缀） | 没有 Maven 模块依赖约束，`domain` import `infrastructure` 仍能编译通过；FF 规则只能靠人自觉，与 ADR-001 的适应度函数思路相悖。 |
| 直接拆分为微服务 | 10 周课程周期内，分布式事务、服务发现、独立部署与运维成本远高于收益，且 Lab 4 明确要求「Spring Boot + Maven 多模块工程」。详见 ADR-001。 |
| 领域对象直接加 JPA 注解（同类共用） | 持久化细节侵入领域模型，聚合被迫暴露无参构造与 Setter，不变式无法保证，退回贫血模型。详见 ADR-008。 |
| 跨上下文直接依赖对方 `domain` / `application` | 形成双向依赖与边界腐化，声誉模块无法独立演进；改为 `*-api` + 集成事件（ADR-002）后，身份模块通过领域事件影响声誉模块，二者不共享事务。 |
