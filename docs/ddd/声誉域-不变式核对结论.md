## 规格 1：开悬赏权限

**测试行为**：

- 学生发起 → `ForbiddenException`；
- 积分 5（<10）→ `BusinessRuleException`；
- 问题已采纳 / 已删除 → `BusinessRuleException`；
- 合法输入 → `expiresAt = now + days`、状态 OPEN。

**实现满足方式**（`Bounty.open` 工厂，`domain/Bounty.java`）：

1. 权限双重校验：`sponsor.role() ∈ {TEACHER, TA, ADMIN}` **且** `sponsorManagesCourse`（应用层由 `IdentityApi.canManageCourse` 注入）→ 任一不满足抛 `ForbiddenException("REP-3001")`；
2. 积分校验：`points < 10 || points > 500` → `BusinessRuleException("REP-1003")`；测试中 5 分命中下限；
3. 问题开放校验：`!questionOpen`（`deleted || acceptedAnswerId != null`）→ `BusinessRuleException("REP-1005")`；
4. 期限校验：`days < 1 || days > 14` → `BusinessRuleException("REP-1004")`；
5. 合法时构造 `new Bounty(null, questionId, sponsor.userId(), points, OPEN, now, now.plus(Duration.ofDays(days)), null, null, null)`——`expiresAt` 精确为 `now + days`，状态 OPEN。

## 规格 2：只能结算一次

**测试行为**：AWARDED 后再 `close` → `ConflictException`。

**实现满足方式**：

- `Bounty.award` / `Bounty.close` 第一步调用私有 `ensureOpen()`：`status != OPEN` → `ConflictException("REP-2001")`；
- AWARDED / EXPIRED 为终态，不存在任何反向迁移路径（无 `reopen` / 状态回退方法）；
- 持久化侧 `BountyRepository.save` 只更新当前聚合快照，不产生第二条记录。

---

## 规格 3：不能赢自己的悬赏

**测试行为**：`sponsorId == winnerId` → `BusinessRuleException`；`isDue` 到期判定正确。

**实现满足方式**：

1. `Bounty.award(answerId, winnerId, now)`：`if (winnerId == this.sponsorId) throw new BusinessRuleException("REP-1006", ...)`；
2. 应用层 `BountyService.settleOnAccept` 捕获该异常后**不报错中断**，而是按状态机转入 EXPIRED：调用 `closeAndRefund`（`Bounty.close` → `ReputationAccount.refundFrozen` → 发 `BountyClosedEvent`），冻结积分退回发起人可用积分——与「被采纳的是发起人自己」的业务语义一致；
3. `isDue(now)`：`status == OPEN && !now.isBefore(expiresAt)`——到期瞬间（`now == expiresAt`）即判定到期，杜绝边界漏判。

## 规格 4：冻结与可用积分守恒

**测试行为**：`open(9, 1000)` → `freeze(300)` 后 `available=700 / frozen=300`；`spendFrozen(100)+refundFrozen(200)` 后 `available=900 / frozen=0`；`freeze(901)`（超额）→ `BusinessRuleException`。

**实现满足方式**（`ReputationAccount`）：

- `freezePoints(p)`：`ensureFrozen(p)` 先校验 `availablePoints - p >= 0`，越界抛 `BusinessRuleException`；随后 `available -= p; frozen += p`；
- `spendFrozen(p)`：`frozen -= p`（悬赏结算转出，不回到可用）；
- `refundFrozen(p)`：`frozen -= p; available += p`；
- 三个方法**只平移**，`available + frozen` 之和在每次操作前后不变（见下方证明）。

**守恒证明（代数推导）**：
设账户初始 `(A₀, F₀)`，记 `S = A + F`。

- 冻结：`A' = A - p, F' = F + p ⇒ S' = (A - p) + (F + p) = A + F = S`
- 花费：`A' = A, F' = F - p ⇒ S' = A + (F - p)`——**注意**：此处 `S` 减少 `p`，因为悬赏积分在 AWARDED 时已转给获奖者（获奖者账户通过 `LedgerEntry` +15/悬赏分入账），系统层面积分不消失，只是换手；
- 退回：`A' = A + p, F' = F - p ⇒ S' = (A + p) + (F - p) = A + F = S`

故对「未结算」路径（冻结 ↔ 退回），`available + frozen` 严格守恒；对「结算」路径（冻结 → 花费），发起人 `S` 减少 `p` 的同时，获奖者通过 `ReputationLedgerService.record(BOUNTY_AWARDED, +p)` 增加 `p`，**系统总积分守恒**。测试断言 `available=900 / frozen=0` 与推导完全一致：`1000 → freeze(300): (700,300) → spend(100): (700,200) → refund(200): (900,0)`。

超额冻结：`freeze(901)` 时 `available - 901 = 700 - 901 < 0` → `ensureFrozen` 抛 `BusinessRuleException`，与测试一致。

## 规格 5：徽章规则（BadgePolicy 纯函数）

**测试行为**：acceptedCount 0 → 空；10 → `{FIRST_ACCEPTED, HELPER_10}`；reputation 150 → `{REPUTATION_100}`。

**实现满足方式**（`BadgePolicy`）：

- `forAcceptedCount(n)`：`n == 0` 空集；`n >= 10` 返回 `[FIRST_ACCEPTED, HELPER_10]`（测试以 10 命中）；
- `forReputation(r)`：`r >= 150` 返回 `[REPUTATION_100]`；
- 授予落库由 `BadgeService.grant` 完成，`BadgeRepository.has` 幂等守卫——重复事件不会重复授徽章。

## 规格 6：学期周期键（AcademicTerm）

**测试行为**：`2026-10-08 → 2026-FALL`；`2027-01-10 → 2026-FALL`；`2027-03-01 → 2027-SPRING`；`monthKey → 2026-10`；`weekKey → 2026-W41`。

**实现满足方式**（`AcademicTerm`，时区 Asia/Shanghai）：

- 学期划分：1–6 月 = SPRING、9–12 月 = FALL；**次年 1–2 月归入上一年 FALL**（`2027-01-10` 的年份回退到 2026），故 `2027-01-10 → 2026-FALL`、`2027-03-01 → 2027-SPRING`；
- `monthKey`：`yyyy-MM`，`2026-10`；
- `weekKey`：ISO 周编号 `yyyy-'W'ww`，`2026-10-08` 所在周为第 41 周 → `2026-W41`；
- 排行榜 Redis 键即按 `termKey / monthKey / weekKey` 构造，保证周/月/学期窗口正确切分。

## 规格 7：声誉规则手册（ReputationRulebook）

**测试行为**：采纳 +15（自问自答不加）；被赞 +10、被踩 −2；改投增量 = 新效果 − 旧效果；每人每自然日（UTC）正向声誉上限 200。

**实现满足方式**（`ReputationRulebook` + 应用层）：

1. `acceptedDelta(answerAuthorId, questionAuthorId)`：`answerAuthorId == questionAuthorId` → 0，否则 +15；
2. `voteDelta(oldValue, newValue)`：按投票取值表（赞=+10、踩=−2、取消=0）计算 `effect(new) - effect(old)`，天然支持改投；
3. `applyDailyCap(delta, gainedToday)`：`gainedToday >= 200` → 0；否则取 `min(delta, 200 - gainedToday)`；
4. 应用层 `ReputationEventHandlers.on(VoteCastEvent)`：正向投票（`rawDelta > 0`）以 **UTC 自然日零点**（`LocalDate.now(clock).atStartOfDay(ZoneOffset.UTC)`）为起点，用 `LedgerRepository.sumPositiveVoteDeltaSince` 统计当日已获正向声誉，再 `applyDailyCap`；负向投票不设上限；
5. 采纳/投票/悬赏等全部计分均通过 `ReputationLedgerService.record`（MANDATORY 事务：查重 → 改余额 → 追加流水 → 发事件 → 授徽章）。

## 答辩要点 A：冻结与可用积分如何守恒

1. **代数不变式**：对任意冻结/退回操作，`available + frozen` 不变（见规格 4 证明）；唯一使发起人 `S` 减少的是「结算花费」，而该减少额同时等额进入获奖者账本，**系统总积分守恒**；
2. **实现保障**：积分变动只有 `freezePoints / spendFrozen / refundFrozen` 三个入口且都挂在 `ReputationAccount` 根方法上，`ensureFrozen` 拒绝超额冻结，杜绝负可用；
3. **对账闭环**：`ReconciliationService.reconcile`（FF-8）定期核对 `reputation == Σ(ledger.delta)`，任何偏离会在 `co_reputation_mismatches` 指标暴露，保证「守恒」可验证而非仅口头承诺。

## 答辩要点 B：Bounty 状态机为何不能跨聚合直接改

1. **聚合边界是事务边界**：`Bounty`（状态机）与 `ReputationAccount`（积分）是两个独立聚合；跨聚合直接改字段会把「悬赏结算」拆成多个原子步骤，中途失败会留下「已 AWARDED 但积分未转」或「积分已转但状态仍 OPEN」的脏数据；
2. **状态迁移必须走聚合根方法**：`award` / `close` 内建 `ensureOpen` 与自赢校验，应用层无法绕过约束；若允许外部直接改 `status`，`ConflictException`（只能结算一次）、`REP-1006`（不能赢自己）等不变式形同虚设；
3. **事件保证最终一致**：`Bounty.award → BountyService.spendFrozen → LedgerEntry 追加 → BountyAwardedEvent` 在同一 MANDATORY 事务完成，跨上下文消费方（如排行榜）通过 `ProcessedEventStore` 幂等消费，重复投递不会重复计分；
4. **可追溯**：所有积分变动先写 `LedgerEntry`（ADR-004），状态机迁移记录 `closedAt / winnerId / answerId`，任何一笔悬赏的来龙去脉可从账本与悬赏记录双向还原。
