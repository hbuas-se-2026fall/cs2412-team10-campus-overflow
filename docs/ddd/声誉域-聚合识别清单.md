## 概述

声誉限界上下文负责「声誉值 → 激励」闭环：问题被采纳、投票获得声誉；开悬赏冻结积分；采纳答案结算悬赏；徽章记录成就。共识别 **4 个聚合**，均位于 `co-reputation-domain` 模块。

| #   | 聚合                | 根实体                                               | 领域文件                            |
| --- | ----------------- | ------------------------------------------------- | ------------------------------- |
| 1   | ReputationAccount | 声誉账户（reputation / availablePoints / frozenPoints） | `domain/ReputationAccount.java` |
| 2   | Bounty            | 悬赏单（OPEN → AWARDED / EXPIRED）                     | `domain/Bounty.java`            |
| 3   | BadgeAward        | 徽章授予记录（userId / type / awardedAt）                 | `domain/BadgeAward.java`        |
| 4   | LedgerEntry       | 声誉账本流水（只追加）                                       | `domain/LedgerEntry.java`       |

## 聚合 1：ReputationAccount（声誉账户）

**根实体**：`ReputationAccount`

| 属性                | 语义                                                         |
| ----------------- | ---------------------------------------------------------- |
| `reputation`      | 账户总声誉值，恒等于该用户 `LedgerEntry` 流水 delta 之和（ADR-004 / FF-8 对账） |
| `availablePoints` | 可用积分（悬赏可冻结额度 + 可消费余额）                                      |
| `frozenPoints`    | 冻结积分（开悬赏时由可用积分转入，结算/到期时释放）                                 |

**关键不变式**：

1. `reputation == Σ(ledger.delta)`（账本流水对账，FF-8 `ReconciliationService.reconcile` 逐账户核对）；
2. `availablePoints + frozenPoints` 守恒：冻结只转移、不创造积分；`freezePoints` 后 `availablePoints >= 0`（`ensureFrozen` 校验），`spendFrozen` / `refundFrozen` 在冻结与可用之间平移；
3. `reputation >= 0`（`requirePositive`，`applyReputation` 前强制校验）；
4. 积分变动必须先写 `LedgerEntry` 流水再改余额（由 `ReputationLedgerService.record` 在同一 MANDATORY 事务内保证），保证可追溯与幂等。

**根方法（工厂 / 命令）**：

- `open(userId, initialPoints)`：开立账户（注册事件触发，初始积分按角色由 `ReputationRulebook.initialPoints` 给出）；
- `applyReputation(delta)`：声誉变动（先 `requirePositive`，再累加 reputation 与 availablePoints）；
- `freezePoints(points)`：冻结可用积分（`ensureFrozen`：超额抛 `BusinessRuleException`）；
- `spendFrozen(points)`：冻结积分支出（悬赏 AWARDED 结算，转出给获奖者，发起人账户不再持有）；
- `refundFrozen(points)`：冻结积分退回可用（悬赏 EXPIRED 退款）。

**存储**：`ReputationAccountRepository`（`findByUserId` / `save` / `findAll` / `topByReputation`）。

## 聚合 2：Bounty（悬赏）

**根实体**：`Bounty`

| 属性                                   | 语义                         |
| ------------------------------------ | -------------------------- |
| `questionId` / `sponsorId`           | 被悬赏问题 / 发起人（课程管理者）         |
| `points`                             | 悬赏积分（10–500）               |
| `status`                             | OPEN / AWARDED / EXPIRED   |
| `expiresAt`                          | `createdAt + days`（1–14 天） |
| `winnerId` / `answerId` / `closedAt` | 结算信息（终态时填充）                |

**状态机**：

```
OPEN ──问题被采纳（award）──▶ AWARDED（冻结积分转出给获奖者，发起人账户减少冻结）
  │
  ├──到期未采纳（close / expireDue）──▶ EXPIRED（冻结积分退回可用）
  └──被采纳的是发起人自己（award 拒绝 → settleOnAccept 转 close）──▶ EXPIRED（退款）
```

**关键不变式**：

1. 仅课程管理者可开悬赏：`sponsor.role() ∈ {TEACHER, TA, ADMIN}` 且 `IdentityApi.canManageCourse(sponsorId, courseId)` 为真，否则 `ForbiddenException`；
2. 悬赏对象须为开放问题：`!question.deleted() && question.acceptedAnswerId() == null`，否则 `BusinessRuleException`；
3. 积分范围 10–500、期限 1–14 天（`MIN_POINTS` / `MAX_POINTS` / `MAX_DAYS`），越界抛 `BusinessRuleException`；
4. 发起人不能赢自己的悬赏：`winnerId == sponsorId` → `BusinessRuleException`（REP-1006）；
5. 只能结算一次：`award` / `close` 均先 `ensureOpen`，非 OPEN 抛 `ConflictException`（REP-2001）；AWARDED / EXPIRED 为终态不可再变；
6. `isDue(now)`：`status == OPEN && now >= expiresAt` 判定到期。

**根方法**：`open(...)`（工厂，含全部校验）、`award(answerId, winnerId, now)`、`close(now)`、`isDue(now)`、`ensureOpen()`（私有）、`reconstitute(...)`（持久化重建）。

**存储**：`BountyRepository`（`save` / `findOpenByQuestion` / `findDue` / `findLatestByQuestion`）。

## 聚合 3：BadgeAward（徽章授予记录）

**根实体**：`BadgeAward`（不可变 record：`userId / type / awardedAt`）

**职责**：成就徽章授予的只读记录；授予规则由纯函数 `BadgePolicy` 给出，不在聚合内持有可变状态。

**关键不变式**：

1. 同一用户同类型徽章至多一条（`BadgeRepository.has(userId, type)` 幂等守卫，`BadgeService.grant` 已拥有则忽略）；
2. 授予即终态，不撤销不修改（record 不可变）；
3. 授予规则为纯函数：`BadgePolicy.forAcceptedCount`（采纳 10 → `FIRST_ACCEPTED` + `HELPER_10`）、`BadgePolicy.forReputation`（声誉 150 → `REPUTATION_100`）。

**存储**：`BadgeRepository`（`has` / `award` / `findByUser`）。

---

## 聚合 4：LedgerEntry（声誉账本流水）

**根实体**：`LedgerEntry`（不可变 record：`userId / eventId / reason / delta / refType / refId / createdAt`）

**职责**：声誉变化的唯一事实来源（ADR-004：只追加，不 UPDATE / DELETE）。

**关键不变式**：

1. 只追加：不存在对既有流水行的修改或删除路径，持久化层仅提供 insert / 查询；
2. 幂等键 `(eventId, userId, reason)`：事件重复投递时 `ReputationLedgerService.record` 先查重，重复则跳过，保证账本不重复计分；
3. `delta` 与 `reason` 语义绑定（采纳 +15 / 投票 +10 / 踩 −2 / 悬赏结算 +points / 初始积分等）；
4. 流水总量必须对账：`Σ(delta) == ReputationAccount.reputation`（FF-8）。

**存储**：`LedgerRepository`（`exists` / `append` / `sumByUser` / `countByUserAndReason` / `sumPositiveVoteDeltaSince` / `findByUser`）。

## 聚合边界说明（为何如此划分）

- **积分变动必须经由聚合**：冻结/花费/退回只通过 `ReputationAccount` 的根方法，结算只通过 `Bounty` 的根方法；应用层 `BountyService` / `ReputationLedgerService` 只编排调用，不直接改字段——保证不变式（守恒、状态机、幂等）在领域层单一入口执行。
- **跨聚合一致性用事件驱动**：悬赏结算 = `Bounty.award` + `ReputationAccount.spendFrozen` + `LedgerEntry` 追加 + 发 `BountyAwardedEvent`，在同一事务（MANDATORY）内完成，避免中间态。
- **读模型独立**：查询侧视图（BountyView / ReputationProfileView 等）由应用层组装，不反哺聚合状态，见《读模型清单》。
